# Output Parsers

An **Output Parser** converts the raw response generated by an LLM into a format that your application can actually work with.

This is important because LLMs normally produce **unstructured text**, while applications often need structured data such as strings, JSON objects, lists, or validated Python objects.

## Why do we need output parsers?

A normal LLM response might look like:

```text
"The product is good overall.
The sentiment is positive.
Its main advantage is performance..."
```

A program may instead need:

```json
{
  "summary": "...",
  "sentiment": "positive",
  "pros": ["performance"],
  "cons": []
}
```

So the basic flow is:

```text
LLM
 ↓
Raw Text
 ↓
Output Parser
 ↓
Structured Data
 ↓
Application
```

### Key idea

> **Output parsers bridge the gap between natural-language output and machine-readable data.**

## Where does the parser fit?

A typical LangChain workflow is:

```text
Prompt
  ↓
LLM
  ↓
Output Parser
  ↓
Final Result
```

Combined with a template:

```text
Input
  ↓
Prompt Template
  ↓
LLM
  ↓
Parser
  ↓
Application
```

The parser is just another component in the pipeline. Because parsers implement the [Runnable](./09-runnables.md) interface, they compose naturally with everything else.

## Why parsers are especially useful

They are particularly useful when the LLM **doesn't natively support structured output** (see [Structured Outputs](./06-structured-outputs.md)):

```text
LLM
 ↓
Free-form response
 ↓
Parser
 ↓
Required format
```

This lets you use smaller, open-source, or older models that only return text.

## The four important output parsers

LangChain provides many parsers, but four cover most cases:

```text
                Output Parsers
                     │
       ┌─────────────┼─────────────┐
       ↓             ↓             ↓
    String          JSON       Structured
       │                           │
       └──────────────┬────────────┘
                      ↓
                  Pydantic
```

1. **String Output Parser** — extracts plain text.
2. **JSON Output Parser** — returns any valid JSON.
3. **Structured Output Parser** — returns JSON matching a defined schema.
4. **Pydantic Output Parser** — returns a validated Pydantic object.

Each adds another layer of control.

## 1. String Output Parser

The simplest parser. Its job is essentially to extract the textual content from the model response:

```text
LLM Response
     ↓
StringOutputParser
     ↓
String
```

Without a parser, you may need to manually access the response's `.content` attribute. The parser makes this explicit and, more importantly, makes the model's output fit naturally into a chain:

```text
LLM 1 → StringOutputParser → LLM 2 → StringOutputParser → Final Output
```

The parser makes the handoff between components cleaner.

> **String Parser = extract clean text from the LLM response.**

## 2. JSON Output Parser

The **JSON Output Parser** aims to make the model produce JSON:

```text
LLM
 ↓
JSON Output Parser
 ↓
JSON
```

For example:

```json
{
  "summary": "Good product",
  "sentiment": "positive"
}
```

This is much easier for a program to consume than arbitrary text.

### Important limitation

JSON format does **not automatically mean a specific schema**. You might expect:

```json
{ "summary": "...", "sentiment": "..." }
```

but the model could produce:

```json
{ "result": "...", "emotion": "positive" }
```

Both are valid JSON. So:

> **JSON Output Parser gives you JSON, but doesn't guarantee the exact structure you want.**

## 3. Structured Output Parser

The **Structured Output Parser** goes one step further — **you define the expected structure**:

```text
Schema
 ↓
Structured Output Parser
 ↓
Instructions for LLM
 ↓
LLM
 ↓
Structured Response
```

You describe expected fields such as `summary`, `sentiment`, `pros`, `cons`, and the parser instructs the model to follow that structure.

### Structured Parser vs JSON Parser

| Parser              | Focus                    |
| ------------------- | ------------------------ |
| JSON Parser         | Format only ("give me JSON") |
| Structured Parser   | Format **and** shape ("give me JSON with these fields") |

Conceptually:

```text
JSON Parser
    ↓
JSON format

Structured Parser
    ↓
JSON format
+
Expected schema
```

### Limitation of the structured parser

The structured parser improves consistency but does **not provide strong runtime type validation**. If the schema expects `age → integer`, the structured parser focuses primarily on the expected structure rather than fully validating that the value is actually an integer satisfying all your constraints. That is where Pydantic comes in.

## 4. Pydantic Output Parser

The **Pydantic Output Parser** combines schema, validation, and type safety.

You define a Pydantic model representing the desired output:

```python
from pydantic import BaseModel, Field

class Review(BaseModel):
    summary: str
    sentiment: str = Field(pattern="^(positive|negative|neutral)$")
```

Then:

```text
LLM
 ↓
Pydantic Output Parser
 ↓
Pydantic Model
 ↓
Validation
 ↓
Validated Object
```

### Why Pydantic is powerful

Suppose your schema requires `name → string` and `age → integer` where `age > 18`. If the model produces `age = 15`, validation fails. You get a clean error you can log, retry on, or fall back from. This is invaluable in production.

## The four parsers compared

| Parser         | Output          | Schema | Validation |
| -------------- | --------------- | :----: | :--------: |
| **String**     | String          |   ❌   |     ❌     |
| **JSON**       | JSON            |   ❌   |     ❌     |
| **Structured** | Structured data |   ✅   |     ❌     |
| **Pydantic**   | Typed object    |   ✅   |     ✅     |

Think of them as increasing levels of control:

```text
String
  ↓
JSON
  ↓
Structured
  ↓
Pydantic
```

### Progressive mental model

```text
String     → "some text"
JSON       → {"name": "..."}
Structured → {"name": "...", "age": "..."}
Pydantic   → Validated object
```

Each step adds more structure and control.

## Output parsers + prompt templates

Parsers often work together with prompt templates. The workflow becomes:

```text
PromptTemplate
      ↓
Formatted Prompt
      ↓
LLM
      ↓
Output Parser
      ↓
Structured Result
```

Many parsers can also provide **formatting instructions** that are inserted into the prompt so the model knows exactly what shape to produce:

```text
Schema
  ↓
Parser
  ↓
Formatting Instructions
  ↓
Prompt
  ↓
LLM
```

This tells the model, in plain words, what format it should produce.

## Output parsers + chains

This is one of the most important practical uses. LangChain lets you compose:

```text
Prompt → LLM → Parser
```

as a single chain. For example:

```text
Input
 ↓
PromptTemplate
 ↓
LLM
 ↓
PydanticOutputParser
 ↓
Validated Result
```

The result is a reusable pipeline instead of manual intermediate handling.

## Multi-step chains

Parsers become even more useful across multiple LLM calls:

```text
Input
 ↓
Prompt 1
 ↓
LLM 1
 ↓
Parser
 ↓
Structured Result
 ↓
Prompt 2
 ↓
LLM 2
 ↓
Parser
 ↓
Final Result
```

The parser ensures the output from one step is in a predictable format before being passed to the next.

## Output Parser vs Structured Output

This connects directly to the previous chapter.

### Native structured output

If the model supports structured output natively:

```text
LLM
 ↓
Native Structured Output
 ↓
Structured Data
```

### Output parser

If the model doesn't support it natively:

```text
LLM
 ↓
Text
 ↓
Output Parser
 ↓
Structured Data
```

| Aspect                 | `with_structured_output`      | Output Parser                  |
| ---------------------- | ----------------------------- | ------------------------------ |
| Where structure comes from | The model itself          | The parser (post-hoc)          |
| Model support required | Yes                           | No                             |
| Reliability            | Higher                        | Lower                          |
| Works with any model   | No                            | Yes                            |
| Typical use            | Modern chat APIs              | Open-source / local models     |

They are complementary — the first is preferred when available; the second is the fallback that works everywhere.

## Which parser should you use?

A simple decision guide:

```text
Need plain text?                        → StringOutputParser
Need JSON but no strict schema?         → JSONOutputParser
Need a specific structure?              → StructuredOutputParser
Need structure + validation + types?    → PydanticOutputParser
```

## Production considerations

Even with output parsers, don't assume every model response will be perfect:

```text
LLM
 ↓
Malformed Output
 ↓
Parser
 ↓
Parsing Error
```

Production applications should consider:

- Validation
- Error handling
- Retries
- Fallbacks
- Clear formatting instructions
- Model/API reliability (timeouts, rate limits)

## Other output parsers

LangChain also supports parsers for other formats such as **lists**, **CSV**, **Markdown**, and other specialized outputs. The four covered here provide the most important conceptual foundation.

```text
                         User Input

                        PromptTemplate

                    Formatting Instructions
                              ↓
                             LLM
                              ↓
                       Raw Response
                              ↓

              ┌───────────────┴───────────────┐

        Structured Data                  Validated Data
              ↓                               ↓
          Next Chain Step                  Application
```

## Key takeaways

### Output Parser

> Converts raw LLM output into a form your application can consume.

### The four parsers

- **String Output Parser** — extracts plain text and simplifies chaining.
- **JSON Output Parser** — produces JSON but doesn't guarantee a schema.
- **Structured Output Parser** — enforces expected structure (but no runtime validation).
- **Pydantic Output Parser** — enforces structure **and** validates types.

### Most important distinction

```text
JSON        → "Give me JSON"
Structured  → "Give me JSON with this structure"
Pydantic    → "Give me this structure and validate the data"
```

### Final mental model

```text
                  LLM
                   ↓
             Raw Text Response
                   ↓
              Output Parser
                   ↓
        ┌──────────┼──────────┐
        ↓          ↓          ↓
      String      JSON    Structured
                              ↓
                           Pydantic
                              ↓
                         Validated Data
                              ↓
                  ┌───────────┼───────────┐
                  ↓           ↓           ↓
              Database       API        Tool
```

The core idea: **an LLM speaks in natural language, while software needs predictable data. Output parsers are the adapter between the two.**
